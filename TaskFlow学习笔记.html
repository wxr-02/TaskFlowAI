1 · 项目总览:它是什么、用了什么

1.1 一句话定位

TaskFlow AI 是一个 Android 端的 LLM Agent 应用:用户用一句自然语言下指令,大模型负责把它规划成工具调用序列(Function Calling),应用负责安全地在本机执行这些工具(闹钟 / 日历 / 短信 / 天气 / 打开应用……),执行过程中支持「需要确认」「需要授权」的中断与恢复;任务成功后自动把经验写入本地知识库(RAG),越用越懂你。

三个「不是」帮你锚定它的定位:

  • 不是套壳聊天 —— 有持久化任务引擎、权限闸门、中断恢复状态机;
  • 不是玩具 Demo —— 每个能力都在真实华为设备上验证过,踩遍了 EMUI 的坑;
  • 不是黑盒 —— 每个设计决策在源码注释里都有「为什么」,这份笔记把它们系统化。

2.2 一次任务的生命周期(中断与恢复)

提交指令 → LLM 规划 tool_calls → 落库 Task+Steps(PENDING)
  → Worker 顺序执行: step RUNNING → Success? 继续
        ├─ RequiresUserConfirmation → step WAITING_USER + task PAUSED ▸ Worker 结束
        │      用户点[允许] → 持久化 confirmed → 重新入队 → 带确认重放
        ├─ RequiresPermission → step WAITING_USER + task PAUSED ▸ Worker 结束
        │      用户系统授权 → 重新入队 → 重放
        └─ 全部步骤 SUCCESS → task SUCCESS
              ├─ 后台向量化写入知识库(学习闭环)
              └─ 工具结果回灌 LLM → 生成自然语言总结写回任务(Agent 闭环)
把这张图刻在脑子里。整份笔记的后半部分,本质上都是这张图的展开:每一根箭头对应一个类、一次数据库写入或一条协程调度。

2.3 六大核心设计原则

#原则含义落点
1Room 是唯一事实来源任务/步骤的一切状态都有库中一行;Worker 与进程随时可以死,重启后从库里重建执行位置。UI 也靠 Room Flow 实时刷新,而不是自己缓存状态。TaskEntity/StepEntity、所有 DAO 的 Flow 查询、TaskExecutor 的"每步先写库"
2控制流用密封类,不用异常"缺权限""需确认"不是意外,是预设流程,所以用 ToolResult.RequiresXxx 返回值表达;异常只留给真正的意外。编译器用 when 穷尽检查保证不漏分支。ToolResult、TaskExecutor.runSteps、ToolRegistry.execute 的兜底
3人在回路 + 幂等恢复敏感操作先挂起等用户拍板;挂起状态持久化(等什么/等哪些权限/是否已确认);恢复请求带状态守卫,重复点击安全无副作用。StepDao.pause/markConfirmed、TaskExecutor.resumeTask、TaskRepository.enqueueUniqueWork
4双闭环:学习 + 回灌任务全部成功 → (a) 向量化入库供未来检索(RAG 学习闭环);(b) 工具结果回灌大模型生成自然语言总结(Agent 闭环)。两者的失败都不影响任务已成功的状态。KnowledgeRepository.remember、TaskSummarizer.summarize
5运行时配置,请求时刻读取API Key / Base URL / 服务商存 DataStore 并镜像到内存 StateFlow;网络层在"每次请求时刻"读最新值 —— 改设置立即生效,无需重启或重建网络栈。SettingsRepository、NetworkModule 拦截器、LlmClient、LlmApiService(@Url)
6解耦扩展:一处定义,一处注册新增工具 = 实现 Tool 接口 + ToolModule 一行 @IntoSet;Registry/规划/执行/UI 全部零改动。领域模型(ToolDef)与网络模型(ToolDefinition)刻意分离。Tool、ToolModule、ToolRegistry、ToolDef

4.1.1 ChatModels.kt —— OpenAI 兼容协议 DTO(全项目"坑"最密集的文件)

先看这段贯穿整个项目的文件头注释,它解释了序列化策略:

/*
 * OpenAI 兼容协议(DeepSeek / Qwen)的 Chat Completions 数据模型。
 *
 * 所有可空字段都给了默认值 null,配合 Json { explicitNulls = false }:
 * 请求时值为 null 的字段不会出现在 JSON 里(例如不带 tools 就不发 "tools": null),
 * 解析响应时服务端多返回的字段也被 ignoreUnknownKeys 忽略,接口升级不会崩。
 */

核心数据结构(简化版,完整字段见源码):

@Serializable
data class ChatMessage(
    val role: String,
    val content: String? = null,                       // assistant 只发 tool_calls 时可为 null
    @SerialName("tool_calls") val toolCalls: List<ToolCall>? = null,
    @SerialName("tool_call_id") val toolCallId: String? = null,  // role="tool" 时回填,协议配对
)

@Serializable
data class ToolCall(
    val id: String,
    val type: String,          // ⚠️ 故意不设默认值(见下)
    val function: FunctionCall,
)

@Serializable
data class FunctionCall(
    val name: String,
    val arguments: String = "", // 注意是字符串,不是对象!OpenAI 协议的经典坑
)
踩坑 · 全项目最有教学价值的反直觉点:为什么 type 不能有默认值?

Json 配置里开了 encodeDefaults = false —— 序列化时会跳过"值等于默认值"的字段。如果写 val type: String = "function",那么它永远不会出现在 JSON 里;而 OpenAI 协议要求 tool_calls/tools 数组元素必须带 "type":"function",缺了会被 DeepSeek 直接拒绝:

422 Unprocessable Entity: missing field `type`

这个坑出现了两次:阶段 1 的 ToolDefinition.type 和 Agent 闭环回灌时的 ToolCall.type。结论:任何"会被我们重新编码发出"的协议必填字段,都不能带默认值。源码里的注释连报错原文都记下来了:

/**
 * ⚠️ [type] 故意不设默认值(与 ToolDefinition.type 同理):
 * Json 配置 encodeDefaults=false 会跳过"值等于默认值"的字段 ——
 * Agent 闭环把 tool_calls 回灌给模型时,tool_calls 里缺 `"type":"function"`
 * 会被服务端直接 422 拒绝(实测 DeepSeek:"missing field `type`")。
 */

调试技巧(来自实战):OkHttp 开着 BODY 级日志,422 的响应体里会直接说明缺哪个字段,logcat 一抓就有。

4.1.4 LlmClient.kt —— 上层只依赖它,不直接碰 Retrofit

@Singleton
class LlmClient @Inject constructor(
    private val api: LlmApiService,
    private val settingsRepository: SettingsRepository,
) {
    suspend fun chat(messages: List<ChatMessage>, tools: List<ToolDef>? = null): ChatResponse {
        val settings = settingsRepository.settings.value   // ← 每次请求都读最新配置
        requireApiKey(settings)

        val request = ChatRequest(
            model = settings.chatModel,
            messages = messages,
            // 空列表等价于"没有工具":直接省略字段,避免部分服务端对 "tools": [] 报错
            tools = tools?.takeIf { it.isNotEmpty() }?.map { it.toToolDefinition() },
            temperature = LlmConfig.DEFAULT_TEMPERATURE,
        )
        return api.chatCompletion(buildUrl(settings.baseUrl, "chat/completions"), request)
    }

    /** 拼接完整地址(baseUrl 容错:有无结尾斜杠均可) */
    private fun buildUrl(baseUrl: String, path: String): String = baseUrl.trimEnd('/') + "/" + path

    /** 提前给出清晰报错,而不是等服务端返回 401 */
    private fun requireApiKey(settings: LlmSettings) {
        check(settings.isApiKeyConfigured) { "API Key 为空:请先在设置中配置" }
    }
}

三个可迁移的设计手法:① 请求时刻读配置 → 设置即时生效;② takeIf { it.isNotEmpty() } → 空工具列表彻底不发字段;③ check() 提前失败 → 用户看到的是"请先配置 API Key"而不是懵的 401。

@Entity(tableName = "knowledge")
data class KnowledgeEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val instruction: String,          // 历史指令(检索 key)
    val toolSequenceJson: String,     // [{"tool":"set_alarm","arguments":"{...}"}, ...]
    val embedding: ByteArray,         // 向量(Room BLOB)

        if (other !is KnowledgeEntity) return false

4.3 仓库层:TaskRepository —— 全项目最长的单函数

submitInstruction() 是"一句话变成一条后台执行链"的全过程,建议逐行精读:

suspend fun submitInstruction(instruction: String): Long {
    // 1. 先落库一个 PENDING 任务 —— 哪怕随后进程死掉,任务也不会丢
    val taskId = taskDao.insert(TaskEntity(instruction = instruction,
        createdAt = System.currentTimeMillis(), status = TaskStatus.PENDING))

    // 2. RAG:检索相似历史 → 与基础指令拼成带 Few-Shot 的规划提示词
    val history = knowledgeRepository.retrieveSimilar(instruction)
    val systemPrompt = PromptBuilder.buildPlannerPrompt(history)

    // 3. 调 LLM 规划
    val response = try {
        llmClient.chat(
            messages = listOf(
                ChatMessage(role = "system", content = systemPrompt),
                ChatMessage(role = "user", content = instruction),
            ),
            tools = toolRegistry.toolDefs(),
        )
    } catch (e: CancellationException) {
        throw e                                   // ← 协程取消必须重抛,不能被吞
    } catch (e: Exception) {
        // 防呆:规划失败不能把任务留在"待执行"里当孤儿 → 标 FAILED 并把原因写进 answer
        taskDao.setAnswer(taskId, "模型规划失败:${e.message ?: "未知错误"}")
        taskDao.updateStatus(taskId, TaskStatus.FAILED)
        throw e                                   // 继续抛给 UI 弹 Snackbar
    }

    val assistantMessage = response.choices.firstOrNull()?.message
    val toolCalls = assistantMessage?.toolCalls.orEmpty()

    // 4. 保存大模型的文本回答(无需工具时=完整回答;触发工具时=开场话术)
    assistantMessage?.content?.takeIf { it.isNotBlank() }?.let { taskDao.setAnswer(taskId, it) }

    // 5. 分支 A:无需工具 → 纯问答,带着回答直接完成
    if (toolCalls.isEmpty()) {
        taskDao.updateStatus(taskId, TaskStatus.SUCCESS)
        return taskId
    }

    // 6. 分支 B:每个 tool_call 落库为一个步骤(orderIndex=顺序,toolCallId=协议配对)
    stepDao.insertAll(toolCalls.mapIndexed { index, call ->
        StepEntity(taskId = taskId, toolName = call.function.name,
            argumentsJson = call.function.arguments, orderIndex = index, toolCallId = call.id)
    })

    // 7. 入队 Worker 开始后台执行
    enqueue(taskId, TaskExecutionWorker.request(taskId))
    return taskId
}

private fun enqueue(taskId: Long, request: OneTimeWorkRequest) {
    // 每个任务一条串行工作链:同名请求按加入顺序执行(APPEND_OR_REPLACE),
    // 不会出现两个 Worker 并发推进同一个任务。
    workManager.enqueueUniqueWork("task-execution-$taskId",
        ExistingWorkPolicy.APPEND_OR_REPLACE, request)
}
四个值得背下来的手法:① 先落库后规划(任务永不丢);② CancellationException 先单独重抛(协程正确性);③ 规划失败→FAILED+原因(防孤儿任务,这条是后来修复真实 bug 加的,见 §11.15);④ 唯一工作名 + APPEND_OR_REPLACE(同任务串行、天然防并发)。

踩坑 · Hilt 限定符的 use-site target:@ApplicationScope 是自定义 @Qualifier,直接写在 private val scope 上时 Kotlin 可能把它应用到"属性"而非"构造参数",导致 Hilt 解析失败。写 @param:ApplicationScope 明确指向构造参数才是正确姿势。同理还有 @param:Named / @param:ApplicationContext(见 §9.1)。

5.1.2 ToolResult.kt —— 四结局密封类(全项目的哲学基石)

sealed class ToolResult {
    /** 执行成功。message 给用户/LLM 读的自然语言结果 */
    data class Success(val message: String, val data: Any? = null) : ToolResult()

    /** 执行失败(参数错误、系统拒绝、IO 异常等) */
    data class Failure(val error: String) : ToolResult()

    /** 缺少运行时权限:返回需要的权限列表,由上层决定何时/如何申请,工具本身不弹窗 */
    data class RequiresPermission(val permissions: List<String>) : ToolResult()

    /** 敏感操作需要用户确认:prompt 是给用户看的确认文案 */
    data class RequiresUserConfirmation(val prompt: String) : ToolResult()
}
类注释里藏着整条状态机的设计哲学:"后两个状态不是'失败',而是 agent 循环中的正常控制信号 —— 缺权限 → 上层去发起权限申请;需确认 → 上层弹 UI 让用户拍板。所以它们绝不能用异常(throw)表达:异常意味着意外,而这里是预设好的流程。" 这段话说清了"为什么要用密封类返回值做控制流"。用 when 穷尽四分支时,编译器还会强制你处理将来新增的第五种结局。

5.1.4 ToolRegistry.kt —— 注册中心与统一执行入口

@Singleton
class ToolRegistry @Inject constructor(
    private val tools: Set<@JvmSuppressWildcards Tool>,   // Hilt 多绑定集合注入

    private val byName: Map<String, Tool> = tools.associateBy { it.name }

    init {
        // 名字是 LLM 调用工具的唯一钥匙,重复会静默覆盖,属于开发期错误,直接暴露
        require(byName.size == tools.size) {
            "存在重名工具:${tools.groupBy { it.name }.filterValues { it.size > 1 }.keys}"
        }
    }

    suspend fun execute(name: String, argumentsJson: String, context: ToolContext): ToolResult {
        val tool = byName[name] ?: return ToolResult.Failure("未注册的工具:$name")   // ← 防模型幻觉
        return try {
            val args = if (argumentsJson.isBlank()) JSONObject() else JSONObject(argumentsJson)
            tool.execute(args, context)
        } catch (e: CancellationException) {
            throw e                                    // ← 协程取消必须放行
        } catch (e: Exception) {
            ToolResult.Failure("工具 $name 执行异常:${e.message}")
        }
    }
}

private fun findBest(query: String, apps: List<AppEntry>): AppEntry? {
    val normalized = apps.map { it to it.label.lowercase().replace(" ", "") }
    val byPriority: List<List<AppEntry>> = listOf(

        normalized.filter { (_, label) -> label.startsWith(query) }.map { it.first },
        normalized.filter { (_, label) -> query.startsWith(label) }.map { it.first },
        normalized.filter { (_, label) -> label.contains(query) }.map { it.first },

    return byPriority.firstOrNull { it.isNotEmpty() }?.minByOrNull { it.label.length }
}

5.4.1 VectorMath.kt —— 单趟余弦相似度

fun FloatArray.cosineSimilarity(other: FloatArray): Float {
    if (size != other.size || isEmpty()) return 0f
    var dot = 0f; var normA = 0f; var normB = 0f
    for (i in indices) {
        val a = this[i]; val b = other[i]
        dot += a * b; normA += a * a; normB += b * b
    }
    val denominator = sqrt(normA) * sqrt(normB)
    return if (denominator <= 0f) 0f else dot / denominator
}

/** FloatArray → ByteArray(存入 Room BLOB) */
fun FloatArray.toByteArray(): ByteArray {
    val buffer = ByteBuffer.allocate(size * Float.SIZE_BYTES)
    buffer.asFloatBuffer().put(this)
    return buffer.array()
}

① 单趟循环同时累加点积与两个模长(朴素实现要遍历三趟,1024/1536 维时收益明显);② 维度不等/空 → 返回 0f(不抛异常);③ 反序列化时 size % 4 != 0 视为非法返回空数组 —— 所以向量维度可由字节长度推导(size/4),无需额外字段,这是维度自愈的判据基础。

5.4.2 LocalEmbedder.kt —— DeepSeek 无 embeddings 时的离线兜底

object LocalEmbedder {
    const val DIMENSION = 256           // 向量维度
    private const val BIGRAM_WEIGHT = 1.5f

    fun embed(text: String): FloatArray {
        val vector = FloatArray(DIMENSION)
        val normalized = text.lowercase().filterNot { it.isWhitespace() }
        for (char in normalized) vector[hash(char.toString()) % DIMENSION] += 1f
        for (i in 0 until normalized.length - 1)
            vector[hash(normalized.substring(i, i + 2)) % DIMENSION] += BIGRAM_WEIGHT
        // L2 归一化:让余弦相似度与文本长度无关
        ...
    }

    /** FNV-1a 哈希:实现简单、分布均匀 */
    private fun hash(token: String): Int {
        var h = -2128831035        // FNV offset basis 2166136261 的有符号写法
        for (c in token) { h = h xor c.code; h *= 16777619 }
        return h and 0x7FFFFFFF
    }
}

算法:字符 unigram(权重 1.0)+ bigram(权重 1.5,顺序信息更强)经 FNV-1a 哈希投到 256 维,最后 L2 归一化。"明天早上7点的闹钟"与"明天早上8点的闹钟"相似度很高 —— 足以支撑"重复模式学习"这一核心场景,且纯离线、确定性(同一文本永远同向量)。局限也写明:无法理解同义改写与指代,那类语义检索要切 Qwen 的真实 embedding。

5.4.3 KnowledgeRepository.retrieveSimilar —— 检索全流程

suspend fun retrieveSimilar(query: String): List<KnowledgeEntity> =
    withContext(Dispatchers.Default) {              // 计算密集,不阻塞 UI
        val all = knowledgeDao.getAll()
        if (all.isEmpty()) return@withContext emptyList()

        val query = embedDetailed(query)            // 远端优先,失败回退本地(带来源标记)
        val queryVector = query.vector

        // ===== 维度安全:切换服务商后(如本地 256 维 ↔ Qwen 1024 维)旧向量无法比较 =====
        var reEmbedded = 0; var skipped = 0
        val comparable = all.mapNotNull { record ->
            val stored = record.embedding.toFloatArray()
            when {
                stored.size == queryVector.size -> record to stored
                query.fromRemote && reEmbedded < MAX_REEMBED_PER_QUERY -> {
                    val fresh = embedDetailed(record.instruction)      // 用当前引擎重新嵌入
                    if (fresh.vector.size == queryVector.size) {
                        knowledgeDao.updateEmbedding(record.id, fresh.vector.toByteArray())  // 自愈回写
                        reEmbedded++
                        record to fresh.vector
                    } else { skipped++; null }
                }
                else -> { skipped++; null }         // 本地回退向量:跳过不重写,避免污染远端向量
            }
        }

        // 分片并行:chunk → async(Default 池) → awaitAll → 拉平
        val scored = coroutineScope {
            comparable.chunked(CHUNK_SIZE)          // CHUNK_SIZE = 16
                .map { chunk -> async { chunk.map { (record, vector) -> record to queryVector.cosineSimilarity(vector) } } }
                .awaitAll().flatten()
        }

        scored.filter { it.second >= SIMILARITY_THRESHOLD }   // 0.75
            .sortedByDescending { it.second }
            .take(MAX_CONTEXT)                                // Top 3
            .map { it.first }
    }

维度自愈的三个规则(注释原话):① 维度一致 → 直接比较;② 查询向量来自远端且条数未超限流 → 用当前引擎重新嵌入并回写(一次性自愈,MAX_REEMBED_PER_QUERY=20 防止切换服务商后打爆网络);③ 查询向量来自本地回退 → 跳过不重写("避免把远端向量污染成本地向量")。

6 · 执行层精讲:中断/恢复状态机

6.1 TaskExecutor.kt —— 全项目的心脏

类注释开篇即定调: "引擎无内存状态,一切以 Room 为准" —— 每推进一步都先把状态写库;遇到 RequiresXxx 就落库挂起标记后直接返回。因此进程被杀、Worker 结束都不会丢进度,恢复时从库里重建执行位置。

中断语义与 ToolResult 一一对应(注释原文):

Success                  → 步骤 SUCCESS,继续下一步;
Failure                  → 步骤 FAILED,任务 FAILED(终止);
RequiresUserConfirmation → 步骤 WAITING_USER + 任务 PAUSED(等"确认");
RequiresPermission       → 步骤 WAITING_USER + 任务 PAUSED(等"授权")。

6.1.1 入口 executeTask —— 幂等起点

suspend fun executeTask(taskId: Long) {
    val task = taskDao.getById(taskId) ?: return
    if (task.status == TaskStatus.SUCCESS || task.status == TaskStatus.FAILED) return   // 终态忽略
    taskDao.updateStatus(taskId, TaskStatus.RUNNING)
    runSteps(taskId)
}

6.1.2 resumeTask —— 状态守卫 + 批准后"解锁"

suspend fun resumeTask(taskId: Long, stepId: Long, userApproved: Boolean) {
    val step = stepDao.getById(stepId) ?: return
    // 状态守卫:只有仍处于挂起态的步骤才响应"决定",重复/过期的决定直接忽略(幂等)
    if (step.status != StepStatus.WAITING_USER) return

    if (!userApproved) {
        stepDao.updateStatus(stepId, StepStatus.FAILED, "用户已取消")
        taskDao.updateStatus(taskId, TaskStatus.FAILED)
        return
    }

    // 批准:
    // 1) 确认类中断 → 持久化"已确认"标记(重放该步时携带 withConfirmation 上下文,
    //    且该标记跨中断/跨进程有效,不会让用户被重复要求确认);
    // 2) 权限类中断 → 用户已在系统层完成授权,直接清标记重放,执行时再做真实权限复查。
    if (step.pendingType == PendingType.CONFIRMATION) stepDao.markConfirmed(stepId)
    stepDao.clearPending(stepId)
    stepDao.updateStatus(stepId, StepStatus.PENDING, null)

    taskDao.updateStatus(taskId, TaskStatus.RUNNING)
    runSteps(taskId)
}
为什么重复点"允许"是安全的?两层保险:① 本方法开头有状态守卫(非 WAITING_USER 直接忽略);② TaskRepository 用 enqueueUniqueWork(APPEND_OR_REPLACE) 串行化,两次决定不可能并发丢失。这就是"幂等"在协程 + 数据库架构里的具体写法。

6.1.3 runSteps 主干 —— 每一步的完整逻辑

private suspend fun runSteps(taskId: Long) {
    val steps = stepDao.getByTask(taskId)
    for (step in steps) {
        when (step.status) {
            StepStatus.SUCCESS, StepStatus.FAILED -> continue
            // 已完成/已终结:跳过(幂等重放的关键)
            StepStatus.WAITING_USER -> {
                // 还有未决的挂起(不该由普通执行越过),保持暂停
                taskDao.updateStatus(taskId, TaskStatus.PAUSED)
                return
            }
            StepStatus.PENDING, StepStatus.RUNNING -> Unit
            // 可执行(曾执行到一半被杀掉的 RUNNING 也重新执行)← 崩溃自愈的关键设计
        }

        stepDao.updateStatus(step.id, StepStatus.RUNNING, null)   // 先写库,再执行
        val context = if (step.confirmed) toolContext.withConfirmation(step.toolName) else toolContext
        // ↑ 已确认过的步骤用"已确认"上下文重放 —— 这是两段式确认的落点

        when (val result = toolRegistry.execute(step.toolName, step.argumentsJson, context)) {
            is ToolResult.Success -> stepDao.updateStatus(step.id, StepStatus.SUCCESS, result.message)

            is ToolResult.Failure -> {
                stepDao.updateStatus(step.id, StepStatus.FAILED, result.error)
                taskDao.updateStatus(taskId, TaskStatus.FAILED)
                return
            }

            is ToolResult.RequiresUserConfirmation -> {
                stepDao.pause(id = step.id, status = StepStatus.WAITING_USER,
                    type = PendingType.CONFIRMATION, data = null, message = result.prompt)
                taskDao.updateStatus(taskId, TaskStatus.PAUSED)
                return
            }

            is ToolResult.RequiresPermission -> {
                stepDao.pause(id = step.id, status = StepStatus.WAITING_USER,
                    type = PendingType.PERMISSION,
                    data = Json.encodeToString(result.permissions),
                    message = "需要权限:${result.permissions.joinToString()}")
                taskDao.updateStatus(taskId, TaskStatus.PAUSED)
                return
            }
        }
    }

    // ===== 全部步骤完成:任务成功 + 双闭环 =====
    taskDao.updateStatus(taskId, TaskStatus.SUCCESS)

    // 学习闭环:仅"全部步骤成功"的任务入库;失败/取消/挂起中的任务不记录
    knowledgeRepository.remember(taskId)

    // Agent 闭环:把工具结果回灌大模型,生成自然语言总结(总结失败只记日志,绝不影响任务状态)
    if (steps.isNotEmpty()) {
        taskSummarizer.summarize(taskId)?.let { taskDao.setAnswer(taskId, it) }
    }
}

四分支差异汇总表:

分支步骤落库任务落库是否 return
SuccessSUCCESS + message不动(继续循环)否
FailureFAILED + errorFAILED(终止)是
RequiresUserConfirmationpause → WAITING_USER / CONFIRMATION / data=null / message=promptPAUSED是
RequiresPermissionpause → WAITING_USER / PERMISSION / data=权限列表JSON / message="需要权限:…"PAUSED是
三个隐藏考点:① "RUNNING 也重新执行" —— 步骤执行到一半进程被杀,恢复时该步重跑,这就是"崩溃自愈";② 恢复不是从头 —— SUCCESS 的步骤被 continue 跳过,从断点继续;③ 执行顺序 = orderIndex,由 LLM 规划顺序落库决定。

6.2 TaskExecutionWorker.kt —— 无状态的一次性推进器

@HiltWorker
class TaskExecutionWorker @AssistedInject constructor(
    @Assisted appContext: Context,
    @Assisted params: WorkerParameters,
    private val executor: TaskExecutor,
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result {
        val taskId = inputData.getLong(KEY_TASK_ID, -1L)
        if (taskId <= 0L) return Result.failure()

        val resumeStepId = inputData.getLong(KEY_RESUME_STEP_ID, -1L)
        val userApproved = inputData.getBoolean(KEY_USER_APPROVED, false)

        return try {
            if (resumeStepId > 0L) executor.resumeTask(taskId, resumeStepId, userApproved)
            else executor.executeTask(taskId)
            // 无论"全部完成"还是"中途挂起",本次推进使命都已结束,正常返回 success;
            // 挂起后的续跑完全依靠"用户操作 → 再次入队"
            Result.success()
        } catch (e: CancellationException) { throw e }
        catch (e: Exception) { Result.failure() }
    }
}

关键设计:① @HiltWorker + @AssistedInject —— Worker 由系统实例化(不能本类构造注入),appContext/params 用 @Assisted 传入,其它依赖正常注入;② 挂起也返回 success —— 不占后台配额、不重试、不阻塞;续跑靠"用户操作 → Repository 再次 enqueue";③ 入队参数三件套 KEY_TASK_ID / KEY_RESUME_STEP_ID / KEY_USER_APPROVED 决定这次是"新执行"还是"恢复执行"。

// 全局动态权限请求:整屏唯一的 launcher,由 ViewModel 的 Effect 触发,结果回注为 Intent
var pendingPermissionStepId by remember { mutableStateOf(-1L) }
val permissionLauncher = rememberLauncherForActivityResult(
    contract = ActivityResultContracts.RequestMultiplePermissions(),
) { result ->
    val stepId = pendingPermissionStepId
    if (stepId > 0) {
        val granted = result.isNotEmpty() && result.values.all { it }
        viewModel.onIntent(TaskDetailIntent.PermissionResult(stepId, granted))
        pendingPermissionStepId = -1L
    }
}
// 特殊权限:精确闹钟(SCHEDULE_EXACT_ALARM)不是运行时权限,需跳系统设置页授权
val exactAlarmLauncher = rememberLauncherForActivityResult(
    contract = ActivityResultContracts.StartActivityForResult(),
) {
    val stepId = pendingPermissionStepId
    if (stepId > 0) {
        // 返回后让引擎重新执行该步骤(未授予会再次挂起,已授予则继续)
        viewModel.onIntent(TaskDetailIntent.PermissionResult(stepId, granted = true))
        pendingPermissionStepId = -1L
    }
}

LaunchedEffect(Unit) {
    viewModel.effects.collect { effect ->
        when (effect) {
            is TaskDetailEffect.RequestPermissions -> {
                pendingPermissionStepId = effect.stepId
                val needsExactAlarmSettings = Build.VERSION.SDK_INT >= 31 &&
                    effect.permissions.contains(Manifest.permission.SCHEDULE_EXACT_ALARM)
                if (needsExactAlarmSettings) {
                    runCatching { exactAlarmLauncher.launch(Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM)) }
                        .onFailure { exactAlarmLauncher.launch(Intent(Settings.ACTION_SETTINGS)) }
                } else {
                    permissionLauncher.launch(effect.permissions.toTypedArray())
                }
            }
        }
    }
}

private fun operationFor(alarm: AlarmEntity): PendingIntent =
    PendingIntent.getBroadcast(context, alarm.id.toInt(),
        Intent(context, AlarmReceiver::class.java).apply {
            putExtra(AlarmReceiver.EXTRA_ALARM_ID, alarm.id)
            putExtra(AlarmReceiver.EXTRA_LABEL, alarm.label)
            putExtra(AlarmReceiver.EXTRA_TRIGGER_AT, alarm.triggerAtMillis)
        },
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)
踩坑 · PendingIntent 的身份比较:extras 不参与比较!只有 requestCode + 目标组件/action/data 等"过滤字段"决定两个 PendingIntent 是否相等。所以"注册/取消都要命中同一个闹钟"的唯一锚点是 alarm.id.toInt() 作为 requestCode;extras 只是数据载体。FLAG_UPDATE_CURRENT 保证复用时更新 extras,FLAG_IMMUTABLE 是 Android 12+ 的强制要求。

nextOccurrence 算法:今天该时刻(秒/毫秒清零)若已过(<= now,等于也算过)→ 顺延一天。cancel = 系统层 alarmManager.cancel(operationFor(alarm)) + 本地 alarmDao.deleteById(双清)。

8.2 语音双引擎(VoiceInput + VoskVoiceEngine)

为什么需要双引擎

11 · 踩坑与设计决策集(20 条)

这一章是全项目的经验精华 —— 每一条都是开发过程中真实遇到并解决的,或在设计时特意规避的。建议每条都读两遍:第一遍记"结论",第二遍想"如果是我,能不能想到"。

A. 协议与序列化

1. encodeDefaults=false 会跳过"默认值字段" —— 协议必填字段绝不能带默认值 两次踩中

现象:Agent 闭环上线后,回灌请求被 DeepSeek 拒绝:422 missing field "type"。
根因:ToolCall.type 写了默认值 "function",而 Json 配置 encodeDefaults=false 会跳过"值等于默认值"的字段,于是 JSON 里永远没有 "type":"function"。
修复:移除默认值(让字段成为必填)。这是同一类坑的第二次 —— 阶段 1 的 ToolDefinition.type 已经踩过一次。
启示:凡是"会被我们重新编码发出"的协议必填字段,一律无默认值;encodeDefaults=false 是把双刃剑,它省流量但会静默吃掉默认值字段。调试时开 OkHttp BODY 日志,422 响应体会直接点名缺哪个字段。

2. data class 的 ByteArray 字段必须手写 equals/hashCode

现象:向量内容完全相同的两个 KnowledgeEntity 被判为不等。
根因:Kotlin 生成的 equals 对数组字段用引用比较 ==。
修复:手写 equals/hashCode,数组用 contentEquals / contentHashCode。
启示:数组字段(ByteArray/FloatArray…)加上 data class 或 Set/Map 使用场景,等于定时炸弹。

3. FunctionCall.arguments 是 String 不是 JSON 对象

OpenAI 协议的经典反直觉点:工具参数是"JSON 字符串",不是嵌套对象。写成 JsonObject 会在回灌时序列化错形。源码注释特意标了"注意是字符串,不是对象!"。

4. 空 tools 列表要么别发,要么发 null —— 用 takeIf 收口

tools?.takeIf { it.isNotEmpty() }:空列表直接变 null,配合 explicitNulls=false 完全不发该字段。部分服务端对 "tools": [] 会报错,这个写法一次规避所有情况。

B. Android 系统行为

5. PendingIntent 的身份比较:extras 不参与

现象:担心"注册和取消时 extras 不同会不会命中不了"。
根因/事实:PendingIntent 相等性只看 requestCode + 目标组件/action/data 等过滤字段,extras 完全不参与比较。
修复:用 alarm.id.toInt() 作 requestCode 作为唯一身份锚点;extras 只当数据载体,配合 FLAG_UPDATE_CURRENT 每次更新。

6. BroadcastReceiver 的 10 秒限制:异步清理必须 goAsync

现象:闹钟触发后清理登记表的协程可能跑不完 —— onReceive 返回后进程随时可能被回收。
修复:val pending = goAsync() 延长生命周期,协程 finally 里 pending.finish()。漏掉 finish 会导致广播永远"没结束"。

7. 通知渠道声音创建后不可修改 → 换声音必须换渠道 id

渠道 id taskflow_alarm_v2 的 _v2 就是这么来的:第一版渠道的声音不对,Android O 起的渠道属性(声音/重要性)创建即冻结,只能新建渠道 id 让系统把它当"新渠道"重新创建。推论:渠道 id 要设计成"内容版本化"的(taskflow_alarm_v3、v4…),而不是"功能命名"。

8. 华为 EMUI 三个真实坑

  • SET_ALARM 权限:调用系统时钟的 HandleSetAlarm 需要 com.android.alarm.permission.SET_ALARM,不加报 Permission Denial —— 且这是"normal 级权限,安装即授予",声明了就完事。
  • FakeRecognitionService:系统语音识别服务禁止三方绑定,startListening 同步抛 SecurityException —— 更阴的是"不报错也不回调",所以需要 5 秒看门狗兜底(见 §8.2)。
  • 状态栏不显示第三方闹钟:用 setAlarmClock 注册后,dumpsys 里能看到("Next alarm clock"),但 EMUI 的界面完全不渲染第三方闹钟痕迹(状态栏/锁屏/通知栏都对照试验过)。结论:行为正确,显示是 OEM 策略,应用内提供"我有哪些闹钟"查询来补位。

9. am start 默认不重置导航栈 / singleTop 才有 onNewIntent

现象:调试时 adb 注入指令,却停留在旧的详情页;prefill 也收不到。
根因:Activity 已在运行时 am start 只会把它置前,不会重建,也不会调 onNewIntent(除非 launchMode=singleTop)。
修复:Manifest 设 launchMode="singleTop",onNewIntent 里消费 prefill。
调试启示:自动化点击前先 uiautomator dump 拿实时坐标,别用硬编码坐标(列表滚动后全错位)。

10. 后台启动 Activity 限制(Android 10+)

应用在后台时 startActivity 被拦截。本项目的策略:① open_app 场景天然前台(用户刚提交)②闹钟走"直接拉起 try/catch → fullScreenIntent → 高优通知"三保险 ③ startActivitySafely 捕获一切异常如实报告。永远不要让"系统拦截"变成"应用崩溃"。

C. 架构与并发

11. WorkManager 默认初始化 vs HiltWorkerFactory(缺一不可的配置)

Configuration.Provider 提供 HiltWorkerFactory + Manifest 移除 WorkManagerInitializer,两个都做了才算配置完整。只做前者,默认初始化先跑,自定义 Factory 静默失效(见 §9.2)。

12. @HiltWorker 缺 ksp("androidx.hilt:hilt-compiler") 会静默爆炸 重大调试

现象:任务入队后 Worker 创建失败,日志是反射的 NoSuchMethodException,编译期毫无提示。
根因:只加了 dagger 的 hilt-android-compiler,没加 androidx 的 hilt-compiler —— @HiltWorker 的绑定模块由后者(KSP)生成。
修复:依赖里补 ksp("androidx.hilt:hilt-compiler")。
启示:Hilt 的"多编译器"体系(dagger 系 + androidx 系)是两个独立坐标系,报错指向运行时而非编译时的依赖缺失最难查。

13. AGP 9 与 KSP:android.disallowKotlinSourceSets=false

AGP 9 内置 Kotlin 后默认拒绝第三方插件用 kotlin.sourceSets 注册生成目录,KSP/Hilt/Room 全灭。开关写进 gradle.properties 即可,但要理解"这是 AGP 收紧边界的过渡期兼容开关"。

14. 协程 try/catch 第一行必须是 CancellationException 重抛

项目里每一处 catch 都长这样:catch (e: CancellationException) { throw e } 在前,catch (e: Exception) 在后。原因:协程取消是通过 CancellationException 传播的,被通用 catch 吞掉会导致"取消不生效/资源泄漏/状态错乱"。出现位置:TaskRepository / KnowledgeRepository / TaskExecutor 调用链 / ToolRegistry / Worker。

15. 孤儿任务:规划失败必须落 FAILED,不能留在 PENDING

现象:真机使用中发现任务 #7 卡在"待执行"永远不动 —— 规划网络请求失败后异常抛出,任务却已入库为 PENDING,没有 Worker 会认领它。
修复:catch 里 setAnswer("模型规划失败:${e.message}") + updateStatus(FAILED) 再重抛(UI 照常弹 Snackbar)。
启示:"先落库保证不丢"的另一面是"必须保证每条落库记录都有结束条件" —— 状态机不能有无法到达终态的状态。

16. 重复点击"允许"为什么安全(幂等三件套)

状态守卫(resumeTask 只响应 WAITING_USER)+ APPEND_OR_REPLACE 串行化 + confirmed 标记持久化 = 无论用户点几次、进程被杀几次,"已确认"最多生效一次、"过期决定"自动 no-op。

D. 工具与安全

17. 危险默认值:空参数绝不"默认全取消"

现象(设计评审发现):cancel_alarm 最初的空参数语义是"取消全部" —— 模型漏传参数时会静默清空用户所有闹钟。
修复:空参 → 直接 Failure,并在错误信息里列出当前闹钟清单(让 LLM 有机会纠正参数重试)。
启示:面向 LLM 的工具,"参数缺失"的默认行为必须是最保守的那个;错误信息要"带上下文",它同时也是给模型的纠错提示。

18. 工具描述里的中文引号惨案(编译期小坑)

Kotlin 字符串里直接写了 "APP"(ASCII 双引号)→ 字符串提前截断,编译报 Unresolved reference 'APP'。修复:换成中文书名号「APP」。启示:中文文案里嵌英文缩写时,统一用「」。

19. API Key 明文硬编码(反面教材)

LlmConfig.API_KEY 里躺着明文 Key,源码注释自己标了 TODO 待迁移。正确做法:local.properties/BuildConfig 或者干脆只走 DataStore(本项目运行时配置已是主路径,常量只是出厂默认值)。请勿把自己的 Key 提交进版本库(本项目 prompt 文件已 gitignore 的原因之一)。

20. Vosk 中间结果必须累计,否则丢句子

说话停顿会让 Vosk 先产出一次 onResult;只在 onFinalResult 取文本会丢前半句。修复:StringBuilder 累计所有 onResult,最终拼接(详见 §8.2)。

把这 20 条当 checklist 用:下一次你自己写 Agent/WorkManager/闹钟类功能前,先过一遍 A/B/C/D 四组,能省下大量调试时间。

12.2 自测题(18 题,点击展开答案)

1. 为什么 ToolCall.type 不能有默认值?Json 配置 encodeDefaults=false 会跳过"值等于默认值"的字段,有默认值就永远不序列化 → DeepSeek 报 422 missing field "type"。任何会被重新编码发出的协议必填字段都必须无默认值。(§11.1)
2. PendingIntent 用什么做身份?extras 为什么不能用来区分闹钟?身份 = requestCode + 目标组件/action/data,extras 不参与相等性比较。所以闹钟用实体 id 作 requestCode;extras 只是数据载体。(§8.1)
3. 任务执行到第 2 步进程被杀,重开 App 后从哪恢复?会重跑第 1 步吗?不会重跑第 1 步 —— runSteps 会 continue 跳过 SUCCESS 的步骤;第 2 步(状态 RUNNING)会被重新执行(崩溃自愈);整个恢复以 Room 里的状态为准,引擎无内存状态。(§6.1.3)
4. 用户连点两次"允许"会发生什么?为什么?第二次是安全的 no-op:resumeTask 有状态守卫(只响应 WAITING_USER),第一次处理后步骤已回到 PENDING/RUNNING;且入队用 APPEND_OR_REPLACE 串行化。(§6.1.2/§11.16)
5. 切换 DeepSeek → Qwen 后,旧知识库(256 维)如何不崩?检索时比对维度(由字节长度/4 推导):远端查询向量遇维度不符 → 用当前引擎重新嵌入并回写(自愈,单次限 20 条);本地回退向量 → 跳过不重写(防污染远端向量)。(§5.4.3)
6. 为什么"缺权限/需确认"用返回值而不是异常?它们是 agent 循环的"正常控制信号"而非意外;用 sealed class 让 when 穷尽处理、状态可持久化挂起;异常适合真正的意外。(§5.1.2)
7. 通知渠道为什么要 _v2?换铃声该怎么做?渠道创建后声音不可修改;要让已有用户获得新铃声,只能换新渠道 id 让系统重新创建。所以渠道 id 要"内容版本化"。(§11.7)
8. @HiltWorker 缺 androidx-hilt-compiler 会怎样?编译期无提示,运行时创建 Worker 时反射抛 NoSuchMethodException(dagger 与 androidx 两套编译器坐标系不同)。(§11.12)
9. Vosk 为什么必须累计 onResult?说话停顿会让 Vosk 先输出一次中间结果 onResult;只在 onFinalResult 取文本会丢前半句。所以要 StringBuilder 累计全部结果再拼接。(§11.20)
10. 华为设备上系统语音识别器可能怎样失败?三条路径?①同步被拒(SecurityException/null)→ silent 切 Vosk;②startListening 抛异常 → 标记损坏切 Vosk;③派发成功但无任何回调 → 5 秒看门狗判定损坏并要求再按一次。(§8.2)
11. 为什么所有 catch 都要先重抛 CancellationException?协程取消靠 CancellationException 传播;被通用 catch 吞掉会导致取消失效、资源泄漏、状态错乱。(§11.14)
12. cancel_alarm 空参数为什么必须失败而不是"全取消"?模型可能漏参误调用,默认全取消风险过大;失败信息附带当前闹钟清单,让 LLM 有机会纠正参数重试。(§5.2.2)
13. Room @Relation 的坑?orderedSteps 解决什么?@Relation 不保证子查询顺序;TaskWithSteps.orderedSteps 统一按 orderIndex 排序,所有展示/执行都用它。(§4.2.4)
14. 为什么 LlmClient 每次请求都重新读 settings?支持运行时切换服务商/Key/Base URL 即时生效,无需重启或重建网络栈;DataStore→内存 StateFlow 的镜像是同步读取的前提。(§4.1.4)
15. 学习闭环的三个守卫?失败任务入库会怎样?守卫:任务 SUCCESS + 步骤非空 + 所有步骤 SUCCESS。失败/取消/挂起任务入库会污染 Few-Shot,让后续规划学到错误示范。(§5.4.3)
16. 步骤 pause() 为什么必须单条 UPDATE 原子写?拆成多条 UPDATE 会让 Flow 观察者看到中间态(如已 WAITING_USER 但 pendingType 还是旧的),UI 闪出错误界面。(§4.2.5)
17. 不用输入法,如何给 App 注入一条中文指令?adb shell am start -n com.example.taskflowai/.MainActivity --es prefill "指令";依赖 singleTop(前台时走 onNewIntent)+ StateFlow 触发重组。(§7.1)
18. 新增一个"查询电量"工具需要改哪些文件?新建 QueryBatteryTool(实现 Tool,execute 里走 ToolContext)→ ToolModule 加一行 @Binds @IntoSet → (可选)ToolIcon 加图标映射 → 提示词提一句。Registry/引擎/UI 全部零改动。(§6 原则 6)
